# Mistakes nobody reported

Silent failures (money taken and not granted, a drifted ledger, a webhook that returned 200 and did nothing) never become a correction. Find them by reconciling local state against the system of record instead of reading code.

- Pull the provider's own view (API, export, dashboard) and diff it against the local table on the shared identifier. Every disagreement is either a lost effect or a stale local mark.
- Compare each writer's *predicate* for the same transition, not each writer's output. Two paths can both look correct and still disagree on units, on lifetime cases, and on which failure statuses mean paid.
- Count effects against inputs: N invoices opened, M marked paid, K grants written. The gap between the first and last number is the bug, and it survives code review because every individual path is correct in isolation.
- **A cached column is not the source of truth, and its vocabulary drifts.** An old table can store a legacy numeric id where current code stores a name, so code that prefers the cache builds keys from the wrong vocabulary and every effect on the historical rows throws. Prefer the identifier the current code generates, treat the cached column as a fallback, and validate it against the known registry before constructing anything from it. Check the distribution with `GROUP BY`, not one row.
- **A job that retries a deterministic failure forever is its own incident.** Nothing about a permanently broken row changes between attempts. Give the failure a terminal state (mark it failed, stop selecting it) or a backoff, and size the interval against how fast the external state can change. Megabytes of one repeated log message is the tell.
- **A test schema that differs from the real one passes what production silently mangles.** A hand-written test schema can type a column as free text where the deployed table has a fixed list, so a new value passes every check and is stored blank or truncated on a server that is not in strict mode. Query the real column type (`information_schema.COLUMNS`), `GROUP BY` the column for blank or unexpected values, and add a check that the test schema's type equals the type the migration names.
- **A failed import inside a log-and-continue `catch` kills a side path permanently** while the primary effect looks healthy. When a post-success hook fails, check that the helper's path resolves before assuming the remote service is refusing you.
