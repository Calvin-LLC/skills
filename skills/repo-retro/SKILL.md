---
name: repo-retro
description: Review recent agent sessions in this repo for wasted navigation, failed searches, stale docs and command loops. Ranks findings by cost and logs metrics so the next run shows whether fixes worked. Proposes only; edits nothing until approved.
---
# Workflow
1. Enumerate, then export the 10 most recent sessions as Claude Code trace JSONL (secrets redacted by default; leave redaction on):
   REPO_DIR="$(git rev-parse --show-toplevel)"
   rm -rf $TMPDIR/hermes-retro && mkdir -p $TMPDIR/hermes-retro
   session export --cwd "$REPO_DIR" --format trace $TMPDIR/hermes-retro/all.jsonl
   Note which sessions are most recent and use only the newest 10 root sessions. Subagent sessions belong to their parent; compaction summaries ([CONTEXT COMPACTION], [PRIOR CONTEXT]) are not tasks.
   The output path becomes a directory of `<session_id>.trace.jsonl` files, not one file. Cron runs (`cron_*.trace.jsonl`, often most of the population) share the cwd; drop them, then take the newest 10 remaining. A bulk `--cwd` export can print "Redaction failed" and stop at an old date; in that case find root ids from `session export --format jsonl --cwd <repo> --after <date> --yes <file>` (rows with no `parent_session_id` and a non-`cron_` id) and export each with `--format trace --session-id <id>`. If the export printed "Redaction failed", it may still have written files: grep the 10 you will read for `sk-`, `ghp_`, `Bearer `, `password=` before any subagent or script output touches them, report the failure, and never rerun with `--no-redact` unasked.
   In a thin workspace that is not itself a git repo (e.g. hyd-live: a junction farm over auto-work-env), `git rev-parse --show-toplevel` fails silently into an empty REPO_DIR — set REPO_DIR to the workspace path itself. On large populations (sessions with thousands of tool calls), skip the per-session export/subagent split and mine state.db directly instead: one Python pass over deduped tool_call_ids beats N subagents reading transcripts. Run that pass with `session-log-mining`'s `scripts/mine_hermes_sessions.py` — it selects the newest roots, folds in their children, dedupes by call id, and prints the per-session table step 2 asks for.

   Pick roots from the miner, not from the bulk export: the miner reads state.db and found the two newest roots that a bulk `--cwd` export (rows with no `parent_session_id`) did not list, so an export-derived population silently skips the freshest work. Run the miner first, then export operator prompts only for the ids it reports. Pass `--outdir` a Windows path (`$LOCALAPPDATA/Temp/...` resolved by `cygpath -w`); a bash-style root path such as `/<root>/x` is resolved by native Python as `C:\<root>\x`, so the output lands somewhere other than where the miner's own printed path suggests in bash.

   Small or non-code populations: `hermes sessions list --workspace <basename>` prints only the newest rows and ends with `… more not shown`, so it under-counts (it showed 2 rows where the cwd export held 5 roots); count roots with `session export --format jsonl --cwd <backslash path> --yes <file>` instead. If that holds fewer than 10 roots, mine what exists and say so in the report and log row instead of widening to other cwds. `mine_hermes_sessions.py --cwd <backslash path> --exclude <this chat id> <its empty sibling id> --outdir <scratch>` runs directly on the cwd and writes `calls.jsonl` and `sessions.json`; list ids with `session export --format jsonl --cwd <path> --yes <file>` (the chat you are in shows up as a 0-message sibling row). Get the operator's own words per session with `--only user-prompts --session-id <id>`; corrections there (the same instruction given in 2+ sessions) are the best evidence for a "rule exists, nothing enforces it" cluster.
   On this machine the miner sits in the pi-dotfiles skills tree (`%USERPROFILE%\pi-dotfiles\hermes\skills\software-development\session-log-mining\scripts\mine_hermes_sessions.py`). The `%LOCALAPPDATA%\hermes\skills\...` path this note used to give does not hold that file (checked 2026-10-30); find it by name across `~/pi-dotfiles` and the hermes skills dirs instead of trusting a remembered path. Recipes for reading the miner's `calls.jsonl` — the row schema, `flags`-based outcome munging, alias-duplicate and cd-prefix counters — live in `references/mining-recipes.md`; load it before writing any analysis pass against the dump.

2. One subagent per session (task), dispatched in batches of ≤3 (the delegate concurrency cap), each with a structured output schema for the fields below so aggregation is mechanical, for populations small enough to delegate; on a batch mine, read the miner's table yourself instead. Each subagent reads only its own session and returns a compact table, no raw output:
   - orientation calls (read_file, search_files, terminal rg/grep/cat/ls, web_*) before the first patch/write_file
   - files read 2+ times
   - search_files calls with total_count 0 (list the patterns)
   - doc reads followed by an error that contradicts the doc (doc path + what failed)
   - terminal commands run 3+ times (command + failure cause)
   - one-line verdict: what in the repo caused the wasted work

3. Aggregate the tables. Cluster by repeated cause across sessions. Operator prompts include harness wrappers (`[IMPORTANT: ... skill ...]`, `[CONTEXT COMPACTION`, `[ASYNC DELEGATION`, background-process notices, and `[OUT-OF-BAND USER MESSAGE]` which IS the operator); drop the wrappers before counting corrections and keep the out-of-band ones. Also read `git log` for the window: 3+ consecutive `fix` commits on the same symptom and file mean each fix patched one call site, so the proposal is one shared function plus a check that forbids the raw call elsewhere (e.g. `grep -rn 'Beep(' sdk/` outside the one function), not a fifth patch. Rank by total wasted calls. Partition before clustering when the repo changed inside the window — a rewrite, a reset, a mass deletion commit. Friction measured against a tree that no longer exists is not evidence for a fix: report the split, and propose only for causes still present in the current tree. Say plainly when a metric drop is demographic rather than a real improvement.
   Check every surviving finding against HEAD before ranking it. Sessions can predate a restructure: `git log -3 --format='%h %ad %s' --date=short`, then `wc -l` or `ls` the files they re-read and grep the docs for the paths they used. A file that was 1,400 lines then and 7 now, a Makefile verb added since, or a doc that still names the old path turns a proposal from "split it" into "fix the stale pointer". Mark each cluster fixed, stale-doc, or still-open.

4. Map each cluster to a fix:
   - slow find -> pointer from a file the agent already reads (AGENTS.md/README index, module headers)
   - stale or contradicted doc -> repoint it at something that resolves today, or delete it if code is the source of truth. Before deleting, grep the repo's own plans and decision records for the filename: a doc the audit calls an orphan is often already spoken for ("restore the file or repoint the citations"), and deleting it re-creates the dangling citations the audit was supposed to remove. Unindexed is not the same as dead.
   - preventable mistake -> automated check (lint, type, test, hook), not prose. Before assuming a gate covers a class of defect, read what it scopes to: a path gate that checks citation *form* passes clean while fifteen docs cite a deleted file. Extending it to existence checks needs an allowlist for archive and history trees, or it fires on every historical record.
   - expensive repeated search -> rename, split, or add an index
   - missing instructions -> commands and env requirements in AGENTS.md
   - dead prose in steering files -> delete

5. Present the ranked proposals with session ids and call counts. Edit nothing until I pick. Report counts from measured transcripts only; a verdict is a hypothesis and should say so. If AGENTS.md is gitignored, note that only on-disk sessions see it, so pointers placed there do not reach other checkouts.

6. Append to .arch/retro-log.md: date, median orientation calls before first edit, empty-search count, doc-contradiction count, fixes applied. A preflight-only pass (the user asks whether the run would work instead of asking for the run) verifies the prerequisites — root-session count from the backslash-cwd export, the miner's presence, the gates' own exit codes — classifies cleanup candidates, and reports; it writes no log row, because no metric was measured. Compare with the previous entry and say whether the numbers dropped. Measure each metric by the definition the previous entry used; when this pass cannot reproduce that definition, label the row non-comparable instead of printing a fresh number beside the old one — a metric that silently changes definition between runs destroys the only thing the log is for. A session with no file-mutating call has no first-edit index: report it as such rather than folding a sentinel into the median.

7. When the user approves the fixes, implement all of them in the same turn and re-measure; do not rewrite from memory. For an AGENTS.md or docs-map rewrite:
   - Read the current file in full first, and rewrite only the repo-facts section; leave persona and voice sections alone.
   - Re-count every number the doc states, from the repo itself: test collection, `noqa`/`type: ignore`/`eslint-disable`, broad `except Exception`, functions over 80 lines by `ast`, route count from `app.url_map`, supervisord programs by `grep -c '^\[program'`.
   - Build a route table from `app.url_map` and the verb decorators, not from the old table. Check duplicate paths with `app.url_map.bind(...).match(path, method=...)`; the first registered wins.
   - Run every make verb the doc names once, and keep the "run live" list honest.
   - Check mounted vs baked with `docker inspect <id> --format '{{range .Mounts}}{{.Destination}} {{end}}'`, and count files with `ls -A | wc -l`; piping to `head` hides entries and reads as an empty dir.
   - Extract every backticked path from the edited docs and assert each exists, then run the repo's own citation and import checks.
   - If AGENTS.md is gitignored, un-ignore it so the pointers reach other checkouts, and say so in the report.
   - Fix doc-vs-UI label mismatches, and name any other doc that still carries the old label instead of silently editing out-of-scope files.
   - When the file holds only persona and voice text and no repo facts, append one new `## Repo map and working facts` section at the bottom and leave every existing byte alone. Copy the file aside first, append, then `cmp -n <size of the copy>` the copy against the result and require identical. Take the facts from the tree, not from memory: docs index, build scripts, `.vcxproj`/manifest, `git status`, `git worktree list`. Record dirty-tree facts (a forced define, a hard-coded input) with the date and say they are the owner's uncommitted edits, so a later agent neither reverts nor commits them.
   - Windows paths inside Python string literals in those helper scripts need raw strings: `'voss\build'` silently becomes a backspace character so an exact-text replace matches nothing, and `'C:\Users'` is a syntax error. Use `r'...'` or build the path from parts.
   - Write a long section with the file-write tool to the scratch dir, then append it with a small script. A multi-hundred-line heredoc with apostrophes inside `bash -c` dies with `unexpected EOF` before anything is written; confirm the line count changed before assuming the append landed.
   - Decide line endings from bytes: `python -c "b=open(p,'rb').read(); print(b.count(b'\r\n'), b.count(b'\n'))"`. `grep -c $'\r'` in this shell counted every line as CRLF on an LF file, so appending CRLF produced a mixed-ending file that had to be rewritten.
   - After the append, re-grep every `file:line` the new section cites (`grep -n` the symbol in the file) and fix the number. A dirty tree shifts lines by one or two, and a backtick-path existence pass does not catch that.
   - Repo bloat the user wants gone (an untracked folder of old deploy scripts and an exe): move it to a sibling `_archive/<repo>/` outside the repo instead of deleting, unless told otherwise. First `git ls-files <dir> | wc -l` and `git check-ignore -v <dir>` (untracked and ignored are different), grep tracked scripts and docs for the path, and compare file count and size before and after the move. Then repoint the docs that named it. Classify before cleaning: a junction documented in the repo's split map and wired into its gate scripts is workspace topology, and attics and receipt dirs are evidence — neither is bloat. A scratch dir with entries written within the hour is a live work surface another seat may be writing to: defer it and name the deferred command in the report instead of moving it mid-run.
   - Run each command you write into the doc once from the shell the agents use, and read the result, not just the exit code. In git-bash `cmd.exe //c x.bat` opens an interactive prompt, runs nothing and exits 0, so a doc line typed from habit looks fine and silently does nothing; the working form is `cmd.exe /c`. A `.bat` that echoes `Debug|x64` also breaks on the pipe, so drive config loops from a scratch `.ps1`.
   - Fill the rules-and-enforcers table honestly: a rule with no check gets the words "Nothing yet" plus the proposed check, not a prose rule dressed as enforcement.

# Pitfalls
- On Windows, `session export --cwd` matches only the backslash form (`%USERPROFILE%\repo`); the forward-slash form from `git rev-parse` exports 0 sessions and prints no error. Sessions are also keyed to the worktree they ran in, so a linked worktree can show 0-4 sessions while the primary worktree (`git worktree list`) holds the real history: export both, and tell the user the tree the sessions ran against is not the tree at HEAD. `$TMPDIR` is a bash-style root path in bash but native Python resolves it to `%LOCALAPPDATA%\Temp`, so write export files under the scratch dir when Python must read them.
- A count is only as good as its result parser. Matching only JSON-shaped tool output silently drops human-format and blocked results, shrinking the denominator and manufacturing an improvement against a previous pass that counted everything. Count every machine-readable result, state the denominator in the log row, and when the old denominator cannot be reproduced say so instead of printing the ratio beside the old one.
- A family aggregate is not a per-session ratio. A root session plus its children spans many conversations; a property computed over that family (duplicate reads, alias-form joins, repeated commands) reads like a per-session count and will not reproduce when someone recomputes it inside each session. Compute the property in the scope where the behavior happens, write the scope into the log row, and if a previously published number only held at family scope, say so rather than reprinting it.
- A citation into a "deleted" file may land on a live file with the same basename and unrelated content: a moved file keeps its name, and its old line numbers now point at something else. Resolve the basename against the tree before trusting any `file:line`. This reads as valid, so it costs more than a dead path.
- Read a command's own exit status: capture output into a variable, then test `$?`. `cmd | head` returns `head`'s status, so a broken tool reports clean and the claim lands in a ranked proposal. Applies to every "verified" line you publish.
- In repos whose sessions are mostly browser, mail or document automation (over 70% `terminal` calls, almost no `read_file`), orientation-before-edit and empty-search counts barely move. Measure instead: repeated terminal boilerplate prefixes (connect/bootstrap lines counted across calls), heredoc one-off scripts versus how many calls reference the repo's existing reusable-tools directory, and how often the same state files are re-read per session. A tools directory nothing points to is the usual cause. The same shape shows up as the same 5-6 state files (rules, decisions, profile, applied list) re-read 10-40 times per session: the fix is one short rules page whose table pairs each rule with what enforces it, linked from the README, plus a check for the rules that are checkable; do not write another long doc.
- **A claim that looks ungrounded may be grounded in a rendering the search cannot see.** `read_file` returns `49|content`, so a model citing `foo.cpp:49` produces a literal that never appears in any tool output. Counting `path:line` claims as ungrounded that way scored 39% on a tree where the honest number was 2.5%; the first figure was pure artifact. Ground a `path:line` claim on the BASENAME appearing in tool output, never on the literal `path:line` string, and re-derive the number by hand on a sample before publishing it.
- **The same filename can exist twice in one workspace, and the tracked one is not the one you edited.** hyd-live keeps real, untracked `scripts/` and `tools/` directories beside an umbrella that tracks its own copies; a rule written into `hyd-live/tools/gates/RULES.md` lands in a file no repo owns, while `auto-work-env/tools/gates/RULES.md` is the tracked one — and the two can hold entirely different documents. Before editing a "shared" config file, run `git ls-files --error-unmatch <path>` from each candidate repo and `os.path.samefile` the two copies; edit the tracked one and say which you touched.
- **A prose rule with no enforcer is the whole finding.** When the operator says "stop doing X" and X is already forbidden in a loaded steering file, the answer is not a new sentence. Measure the rate (assistant turns matching X / all substantive turns), check when the rule was added with `git log` on the steering file, and split the corpus pre/post that commit: if the rate is flat, the rule never worked and the change is an enforcer, not wording. Say plainly that the rule existed and was ignored.

- Before proposing a new wrapper for repeated boilerplate, search the sibling tool directories and the machine-level helper dir for an existing launcher (for example a `work_chrome.py ensure`); the wrapper should call it rather than re-implement start-up, and the proposal should name it.
- A directory listed in `.git/info/exclude` or `.gitignore` (check with `git check-ignore -v <dir>`) cannot get a CI gate or a committed fix; say that in the proposal and make any new check a runnable script inside that directory with the pointer placed in a file the agent already reads there.
- A steering doc can describe a codebase that no longer exists (file names in `.claude/CLAUDE.md` with no match in `ls`). No session will show friction from it because agents ignore it; catch it with a static pass that extracts the backticked filenames and tests each one, and report it as its own row, not as a measured session cost. Resolve each candidate against the doc's own directory plus the project subfolders before calling it dead, and discard non-paths (`acquire/release`, `g.mutex`, `a.h/.cpp` shorthand, bare filenames that live on a remote machine); the raw count over-reports by roughly a third, so hand-check the list before publishing it.
- Orientation-before-edit counts every non-mutating call, and in terminal-heavy sessions that includes builds, probe runs and `git log`. Before blaming docs for an outlier (100+ calls, zero `read_file`), print the first 15 command heads of that session: context-rebuild commands (`git log`, `ls`, `cat AGENTS.md`) point at a missing map, while build and probe runs are real work. Say which it was and label the cause a hypothesis.
- The first log row has no predecessor: write "first entry" and the definitions used (what counts as an edit, which sessions were excluded) so the next run can reproduce them.
- Wall-clock cost is not tool-call cost: sleeps, VM recovery scripts and terminal-polling loops can dominate a session while producing few distinct commands. Report them as their own category; they rarely map to a doc fix, and folding them into the call ranking buries the real finding.
- Analyse miner dumps with a script written to the scratch dir via the file-write tool, then `python <script>` — never as a multi-line heredoc through the terminal. A heredoc eats backslashes inside Python string literals (the first run dies on a SyntaxError before producing anything) and one wrong delimiter ends the block mid-script. The scratch file preserves the source byte-for-byte and survives the turn for a second pass.
